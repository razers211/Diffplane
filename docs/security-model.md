# Security model

Diffplane can change the configuration of every switch in a data centre. Treat the server that
runs it, its databases and its backups as you would the switches' own admin access.

**Use at your own risk, and test in a lab first.**

## What protects the switches

- **Never deploy without a diff.** Every change is generated, diffed and shown as the exact patch
  before a person approves it. Each switch's patch is recomputed just before it is sent and must
  equal the approved one; otherwise nothing is sent.
- **Deploys are off by default.** `DEPLOY_ALLOWED_SITES` is empty: no fabric receives a deploy
  until an admin turns deploys on for it (typing the fabric's name). Imported and new fabrics
  start diff-only.
- **Pinned host keys.** Diffplane talks to a switch only once a person has compared its SSH host
  keys with the switch's console and an approver has pinned them in NetBox. Annet (port 22), the
  collector and every read (port 830) refuse a switch that is not pinned or presents another
  key. gnetcli is built with `deploy/gnetcli/known-hosts.patch` because upstream does not verify
  host keys.
- **The management plane is never managed.** No generator touches MEth, the management VPN
  instance (`_management_vpn_`) or its default route, or the platform's own AAA accounts, so a
  bad deploy cannot lock the platform out. The only opt-in exceptions, off by default: people's
  login over RADIUS (deployed one switch at a time under a self-reverting `commit trial`, taken
  back if the platform cannot log in again) and local accounts the platform itself created.
- **Reads are read-only.** The collector only sends NETCONF `<get>`. Where the CLI is needed for
  reads (imports, route view), only commands from fixed `display` allow-lists are sent.
- **Intent freeze.** While a deploy is approved or rolling out, intent writes are refused, so
  nothing unapproved can slip into a running rollout.
- **Waves.** A rollout never touches both switches of an M-LAG pair at once, and stops starting
  new switches at the first failure.

## People and the API

- Every endpoint except `/health`, signing in and first-time setup needs a session. `/metrics`
  needs Prometheus' bearer token (`METRICS_TOKEN`, generated by `deploy/gen_env.py`). Sessions
  are server-side; the cookie is `Secure`, `HttpOnly`, `SameSite=Strict`, and expires
  (`SESSION_TTL_HOURS`, 12 by default).
- Writes whose `Origin` names another site are refused, and every answer carries a strict
  Content-Security-Policy and the usual security headers.
- After 10 failed sign-ins from one address in 15 minutes, that address waits (`429`).
- Local passwords are stored as scrypt hashes (N=2^17, r=8, p=1); older, weaker hashes are
  upgraded at the next successful sign-in. Active Directory (LDAPS, with the CA you give) and
  RADIUS can be used instead; local accounts always work, so keep a local admin as break-glass.
- Roles: viewer < operator < approver < admin, and optional per-fabric limits. Approvals,
  host-key pins and every intent change are recorded in the audit trail, which the API cannot
  edit.
- First-time setup is unlocked only by a one-time code printed in the orchestrator's log, and
  only while no account exists.

## Secrets

- No secret lives in the repository. `deploy/gen_env.py` writes `deploy/.env` with random values
  (mode 0600, gitignored); device credentials and NetBox tokens come from environment variables,
  or from Admin › Settings, where they are write-only.
- Secret values that generators put into config are masked in everything the API returns
  (`orchestrator/redact.py`); stored running configs are encrypted with `CONFIG_BACKUP_KEY` and
  shown masked.
- **Database backups contain secrets** (NetBox API tokens, password hashes, settings). Keep
  `deploy/backups/` private and encrypt copies you move off the host.
- Deploy transcripts inside the orchestrator container (`/tmp/annet-deploy-logs`) contain
  device secrets in plain text; they are lost when the container is recreated.

## Network exposure

- Only the orchestrator is published (HTTPS only, a self-signed certificate it makes and renews
  itself; compare its fingerprint before trusting it, or import it into your trust store).
  NetBox, Postgres, Redis, Prometheus, Alertmanager and ClickHouse stay on the Compose network.
- The optional receivers (NetStream, syslog, the SFTP image server, ZTP) publish a port only when
  you set their bind address. Docker's published ports bypass host firewalls such as ufw: filter
  in front of the server if needed.
- The syslog receiver drops datagrams from unknown sources; the SFTP server hands out one-time
  accounts per download.

## Known risks

- **Zero-touch provisioning** sends a first-boot config with the platform's account passwords
  in clear over TFTP on the management network, from registration until the switch is approved
  or its provisioning window ends (`ZTP_WINDOW_HOURS`, 24 by default; register it again to
  serve it again).
  dnsmasq answers only registered MACs, never from a pool, and the TFTP server serves each
  address only its own folder; a host deliberately taking a registered switch's address before
  it boots could still fetch that file. Keep ZTP stopped when no switch is waiting, and keep the
  management network trusted.
- **SNMP v2c** (the default) sends the community in clear; SNMPv3 readers are available per
  fabric.
- **NetBox 4.4** stores classic API tokens unhashed.
- Multi-device behaviour has only been verified on a single lab switch (see
  [supported switches](supported-switches.md)).
